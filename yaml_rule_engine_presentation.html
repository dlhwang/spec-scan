1. 문제 제기 (1~2분)

왜 제네릭 YAML 룰 엔진을 도입하려 하는가?

하드코딩된 Java 엔진의 한계 극복 및 시멘틱 메타 룰의 외부화

현재 한계 (As-Is: Java Hardcoding)
  • 배포 종속성: 새로운 검출 로직이나 프레임워크 패턴 추가 시 엔진 재빌드 및 v2/v3 배포 필수
  • 경계 모호성: 저장소 특정 업무 룰(quantity < 0)과 공통 시멘틱 구조가 자바 코드에 엉킴
  • 관리 버든 폭발: 수천 개 메서드 이름을 자바 코드로 일일이 예외 처리 시 유지보수 불가능
목표 상태 (To-Be: Generic YAML Engine)
  • 제네릭 Classifier 외부화: if-throw, Null Guard, Enum 등 공통 메타 룰만 YAML로 선언
  • 코드 수정 0건: 새로운 룰 패키지 추가 시 엔진 배포 없이 즉시 로딩 및 검증
  • Runtime Dynamic Binding: 실제 DTO 필드명, 상수값은 CodeGraph에서 동적으로 바인딩

3. 정직한 경계 긋기 (2~3분)

이번 PoC에서 하지 않는 것 (Non-Goals)

과도한 튜링 완전 DSL 발명의 덫을 피하는 명확한 스코프 제한

🚫 튜링 완전 Script 금지

YAML 내에 if/else, 자바 람다, 임의의 스크립트 표현식을 넣는 복잡한 언어를 만들지 않습니다. 오직 유한한 Primitive연산자 조합만 허용합니다.

🚫 Fact Generation 외부화 금지

소스코드를 AST/CodeGraph 노드로 파싱하고 그래프를 생성하는 최하위 백엔드 엔진 알고리즘은 자바 고성능 엔진에 남겨둡니다.

🚫 업무 의미 억지 추측 금지

CodeGraph 상에 근거(Evidence)가 없는 의미를 룰로 추측하지 않습니다. Graph가 끊기면 PARTIAL_ANALYSIS로 명시적 보고합니다.

오버 엔지니어링 점검 및 AI 하이브리드 전략

룰기반(YAML)과 AI기반(CodeGraph+LLM)의 효율적인 역할 분담

추출 방식별 비교 분석 데이터

안전장치: Golden Corpus Gate
YAML 룰 수정 시 미리 확보된 표준 Spring MVC 테스트용 저장소(Golden Corpus)에 대해 자동 회귀 검증을 거친 후 승인된 룰만 런타임에 동적 반영합니다.
하이브리드 전략: 정밀 구문 정규화는 YAML 엔진이 담당하고, 정규화된 데이터 기반 문장 요약은 AI가 담당하여 효율 극대화.
