00 Progressive Externalization

코드 실행 경로에서
테스트 가능한 조건을 추출한다

Spring 소스코드 → Fact Code Graph → 테스트 계약.
오늘 이야기의 중심은 무엇을 만들었나가 아니라 왜 이 구조가 되었나입니다.

이 발표를 관통하는 한 문장 어려운 문제는 “조건을 어떤 포맷으로 적느냐”가 아니라, “코드 속 조건이 어떤 API 입력에서 왔고 무엇을 의미하는지 증명하는 것”이었다.
쉽게 말해 — 코드는 “비밀번호가 틀리면 거절한다”고 말합니다. 이걸 테스트로 쓰려면 그 ‘비밀번호’가 요청서의 어느 칸(BODY의 $.password)에서 온 값인지까지 기계가 스스로 증명해야 합니다. 지금은 이 증명(증적)이 아직 완전하지 않습니다. 증명 못 한 조건을 활용(YAML 외부화)부터 하는 건 순서가 뒤바뀐 것 — 그래서 코드 단계의 정합성 개선이 먼저입니다.
대상 Spring REST API 출력 preconditions · assertions · business rules · diagnostics 시간 약 10분
01 어노테이션은 절반만 알려준다 WHY ①

쉬운 절반은 이미 된다. 문제는 나머지 절반.

▚ 어노테이션으로 얻는다 — 쉬움
  • HTTP method / path
  • PATH · QUERY · HEADER · BODY 바인딩
  • request / response DTO 스키마
  • Bean Validation (@NotNull 등)
▚ 실행 경로에만 있다 — 어려움
  • 비밀번호 일치 여부
  • 리소스 존재 여부 (Optional lookup)
  • 권한 · 상태 전이 조건
  • 낙관적 락, 도메인 불변식
requestPreconditions (요청 사전조건)
요청 값이 충족해야 할 조건 → negative test
responseAssertions (응답 보장 조건)
정상 응답이 보장하는 것 → status·body 검증
excludedBusinessRules (제외된 비즈니스 규칙)
요청 값만으론 못 만드는 외부 상태 → 사전 데이터
diagnostics (진단)
끝까지 증명 못 한 후보 → 품질·사람 검토
이 슬라이드의 Why왜 실행 경로까지 파고드나? — 어노테이션 밖에 진짜 테스트 조건이 있으니까.
02 YAML을 먼저 해봤다, 그런데 WHY ②

YAML PoC — 문제는 포맷이 아니었다

- id: DOCUMENT_EDIT_PERMISSION
  match:
    predicateType: BOOLEAN_CALL
    methodName: canEdit    # ← 이름 매칭
    failureOutcome: THEN
  output:
    category: AUTHORIZATION
    constraint: { kind: CONTROL_FLOW_ONLY }
  • canEdit는 매칭했다 — 그래서 이 조건이 어떤 API 입력에서 온 거지? YAML은 답을 못 한다.
  • CONTROL_FLOW_ONLY로 찾긴 했는데 — 요청 값 제약인지 외부 권한 상태인지 구분이 안 된다.
  • 이 판단까지 전부 YAML에 넣으면 — YAML이 또 하나의 프로그래밍 언어가 된다.
✕ 잘못된 표현: “YAML 룰 엔진은 아직 구현 안 됐다.” ✓ 정확한 표현: 실행 가능성은 PoC로 검증하고자 했고, 그 덕분에 무엇을 외부화하면 안 되는지가 드러났다.
이 슬라이드의 Why왜 YAML로 아직 못하나? — 해봤더니 포맷화 단계 이전에 의미 해석이 진짜 문제였으니까.
03 문제를 피부로

if (...) throw ... — 이 한 줄을 어떻게 테스트로 만드나

1 비밀번호 검증 — Service
if (!passwordEncoder.matches(request.password(), member.password()))
    throw new InvalidPasswordException();
2 리소스 존재 — Repository
Order order = orderRepository.findById(orderNo)
    .orElseThrow(OrderNotFoundException::new);
3 도메인 상태 전이 — Domain
if (!order.isShippingChangeable())
    throw new IllegalStateException();

테스트에 필요한 조건은 Controller의 어노테이션이 아니라, Service·Domain 실행 경로 깊숙이 숨어 있다. 오늘 이야기는 이 세 줄을 실행 가능한 테스트 조건으로 바꾸는 과정에 있어서 어려움을 보여주고자 한다. 이 1 · 2 · 3이 분석 파이프라인의 어디를 지나가는지도 곧 전체 지도로 확인한다.

04 진짜 질문은 여섯 개였다 전환점

호출 하나를 테스트 조건으로 바꾸려면

1  if (!passwordEncoder.matches(request.password(), member.password())) throw ...
2  orderRepository.findById(orderNo).orElseThrow(OrderNotFoundException::new)
3  if (!order.isShippingChangeable()) throw ...
같은 여섯 질문 — 세 예시의 답은 전혀 다르다
질문 1 matches 2 orElseThrow 3 isShippingChangeable
1. 실패 분기는 then인가 else인가?then에서 throw분기 없음 — 빈 결과면 throwthen에서 throw
2. !·위임 메서드로 polarity가 뒤집히나?! 1회 — false가 실패반전 없음 — 부재 자체가 실패! 1회 — false가 실패
3. 값은 Controller의 어느 인자에서 왔나?BODY DTO의 passwordPATH 인자 orderNo요청 값 아님 — DB에서 온 도메인 상태
4. 실제 HTTP wire name은?password{orderNo}해당 없음
5. BODY라면 정확한 JSONPath는?$.password해당 없음 (PATH)해당 없음
6. 요청 값 제약인가, 외부 선행조건인가?요청 값 제약 → requestPreconditions외부 리소스 존재 → excludedBusinessRules외부 선행조건 → excludedBusinessRules
이 슬라이드의 Why여섯 질문은 전부 데이터 흐름과 그래프 탐색 문제다. 이름 매칭은 1번에도 답 못 한다. 그리고 지금도 이 여섯 질문에 끝까지 답하지 못해 diagnostics로 남는 후보가 있다 — 활용(YAML)으로 넘어가기 전에, 코드 단계의 증명부터 단단해져야 한다.

06 여기까지의 결론 — 오늘의 주된 주장 주장

증명하지 못한 조건은, 활용할 수 없다

그래서 활용(YAML 외부화)보다
코드 단계의 정합성 — 증명 — 개선이 먼저다.
  • 어노테이션은 절반만 알려준다 — 진짜 조건은 Service·Domain 실행 경로에 있다
  • YAML PoC — 벽은 포맷이 아니라 의미의 증명이었다
  • 예시 세 줄 같은 케이스가 모든 컴포넌트에 다양한 형태로 포진해 있다
  • 그리고 지금도 증명이 끊겨 diagnostics로 남는 후보가 있다
1 코드 단계 정합성 증명 — 지금 여기→ 2 검증된 의미만 YAML 사전으로→ 3 미등록 long-tail은 LLM fallback
한 번 더, 기획 언어로기계가 “이 조건이 요청서의 어느 칸에서 온 값인지”를 스스로 증명하지 못하면, 그 조건으로 테스트를 만들 수 없다. 증명이 완전해진 뒤에 활용(YAML·LLM)을 넓히는 것이 순서다. 이어지는 Appendix의 구조 이야기는 전부 이 증명을 가능하게 만드는 장치다.

07 그래서 Fact Code Graph 하나로 WHAT ①

왜 하나의 그래프인가 — 공정한 비교를 위해

Spring Source
↓
Canonical Fact Code Graph
↓
Predicate Candidate + Evidence
↓
Deterministic Rule
LLM Interpretation

예전엔 endpoint · validation · output 분석이 서로 다른 중간 모델을 봤다. 같은 사실이 중복되고 변환 중 손실됐다. 이제 호출 관계·조건·데이터 흐름·DTO 스키마를 하나의 사실로 기록한다.

budget전부 넣지 않는다. 내부 비즈니스 메서드는 본문까지, JDK·Spring·라이브러리는 호출 사실만. 못 푸는 건 조용히 버리지 않고 diagnostic으로 남긴다.
이 슬라이드의 Why왜 그래프를 통합했나? — Rule과 LLM을 같은 잣대로 비교하려면 같은 사실·같은 evidence를 봐야 하니까. 그래야 정확도·재현성·비용을 공정하게 잰다.
08 그래서 “증명 수준”으로 출력 WHAT ②

왜 함부로 내보내지 않는가

Candidate
├─ 구조 미지원        → diagnostics
├─ 의미 미해결        → diagnostics
└─ 의미 해결
   ├─ REQUEST_REQUIREMENT  → requestPreconditions
   ├─ RESPONSE_GUARANTEE   → responseAssertions
   └─ BUSINESS_RESTRICTION → excludedBusinessRules

출력은 ‘찾았다/못 찾았다’가 아니라 어디까지 증명했나로 갈린다. 의미까지 증명된 것만 실행 가능한 계약으로 나간다.

신뢰coverage 숫자를 올리려고 추측을 실행 가능한 테스트 조건으로 내보내는 순간 도구는 신뢰를 잃는다. 못 푼 건 정직하게 남기는 게 낫다.
계층이걸 가능하게 하려고 책임을 나눴다: 사실 기록 · 후보 수집 · 의미 분류 · target 연결 · 출력 귀속.
이 슬라이드의 Why왜 증명 수준으로 나누나? — 도구의 신뢰는 “정직하게 모른다고 말하는 것”에서 나오니까.
09 그래서 이렇게 나눈다 WHERE

YAML은 그래프 탐색 언어가 아니라 “프로젝트 의미 사전”

엔진(코드)에 남긴다YAML로 외부화한다
AST · Fact Graph 생성method / signature alias
data-flow · origin 역추적argument의 semantic role
polarity · outcome 분석category / effect / operator
wire name · JSONPath 계산프로젝트별 vocabulary
dedup · diagnostic lifecycleexception → 도메인 의미
 
- id: PASSWORD_MUST_MATCH
  match:
    ownerType: ...security.crypto.PasswordEncoder
    method: matches
    arguments: [ {role: rawValue}, {role: encodedValue} ]
    failure: { negated: true, throws: "*InvalidPasswordException" }
  output:
    category: AUTHENTICATION
    effect: REQUEST_REQUIREMENT
    targetFromArgumentRole: rawValue
    # 엔진이 origin 역추적 → $.password 계산
원칙Java 엔진은 “무슨 일이 일어났는가”를 구조적으로 증명하고, YAML은 “이 구조가 이 프로젝트에서 무슨 의미인가”를 선언한다. 검증된 것만 점진적으로 외부화한다.
10 핵심 산출물, 그리고 결정 요청

규칙 목록이 아니라 “사실 → 계약” 파이프라인

핵심 산출물은 거대한 규칙 목록도 YAML 문법도 아니다. 소스코드를 공통 사실(Fact Code Graph)로 바꾸고, 그 사실을 테스트 계약으로 번역하는 의미 파이프라인이다. Rule · YAML · LLM은 경쟁이 아니라 역할이 다르다. 순서도 분명하다 — 코드 단계의 증명 정합성을 먼저 끌어올리고, 검증된 의미부터 YAML로 활용한다.
